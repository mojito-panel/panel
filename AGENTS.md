# AGENTS.md — Mojito Panel Project Conventions

Game server hosting panel, native Windows, no Docker.
Single project (TanStack Start). The agent (**shard**, Go daemon, one per machine) is a SEPARATE, external codebase — not part of this repo; the panel talks to it over HTTP/WS.

## Commands

```bash
npm install                    # Dependencies (Node 24 required)
mise run setup:dev             # Docker Postgres + copy .env.default → .env
npm run db:migrate             # Generate a MikroORM migration (applied at boot by src/server.ts)
npm run dev                    # Panel — http://localhost:5173 (strictPort)
npm test                       # All tests
npm run build                  # Panel build (vite, client + SSR)
```

## Architecture

- The panel NEVER touches game servers directly — it talks to the agent via API.
- The panel ↔ agent contract is defined in `src/contract` (shared Zod schemas) — it is the authoritative reference for the external agent's API.
- The agent is a generic daemon — nothing game-specific in it.

## Language

- **Code comments**: in ENGLISH (`src/` and `tests/` alike).
- **Tests**: in ENGLISH — descriptions, assertion messages, variable names in fixtures.
- **Docs**: in ENGLISH.
- Runtime error messages addressed to the end user (e.g. `PowerActionError('Serveur inconnu')`) stay in French.

## Stack & versions

| Technology | Constraint |
|---|---|
| Node.js 24 | `pg` (Postgres) — NO better-sqlite3 (does not compile on Windows) |
| TypeScript | `erasableSyntaxOnly: true` everywhere — NO parameter properties, enums, namespaces |
| Visibility | Private fields/methods with `#` (native JS syntax) — NEVER `private`/`public`/`protected` |
| React 19.3 | NO `useCallback`/`useMemo`/`forwardRef` — React Compiler enabled |
| MikroORM v7 | `defineEntity`/`p` (decorator-less) — NO EntitySchema, NO decorators |
| better-auth | `pg` Pool + snake_case mapping (`user.fields` etc.), `tanstackStartCookies` plugin — tables managed by MikroORM |
| Zod 4 | Standard Schema — TanStack Form's native validator (no adapter) |

## Panel conventions

### Structure

```

├── components/app-sidebar.tsx  # Consolidated sidebar (dashboard/admin/server variants)

├── db/
│   ├── entities.ts    # ALL MikroORM entities in ONE file
│   ├── types.ts       # Inferred types: `interface IUser extends InferEntity<typeof User> {}`
```

### Rules

- **Forms**: TanStack Form + Zod (`useForm` + `validators: { onChange: schema }`), mutations via `useMutation`. NEVER `useState` for form fields. Schemas in `src/validators/`, types `XxxDto = z.infer<...>`. Reactive read of a form value: `<form.Subscribe selector={(s) => s.values.x}>`, write: `form.setFieldValue`. No `z.coerce`/`z.default()` in form schemas (incompatible with TanStack Form's Standard Schema typing).
- **Lists (data tables)**: EVERY list is the shared table — NEVER a hand-rolled `<table>`. One module per list in `src/lists/` declares it ONCE with `defineList`: the columns (header + `cell(row, context)`), and per column its `sort` (`field('s.name')`, or `field('u.email')` through a join) and its `filter` (`text` / `choice` (static or `dynamic` page-supplied options / `boolean` / `nullable` — IS NULL, for a free allocation or an unowned row); values are always the STRING wire form `'a,b'`, `'true'`), the `searchTargets` of the `q` box, the single-row `joins` and the `defaultSort`. The same module derives the Zod query schema, so a route (`validateSearch`), the server function (`.validator()`) and the query key all share it: the UI's columns and the SQL's filters cannot drift, and a client string NEVER reaches the ORM (filters/sorts are the list's allowlist). State lives in the URL (`validateSearch: (s) => list.querySchema.parse(s)`, `stripSearchParams(list.defaultSearch)`, `useNavigate({ from: Route.fullPath })` + `mergeQuery(search, patch)`, `useQuery(['<list-name>', search], { placeholderData: keepPreviousData })`) and the page renders `<DataTable list rows rowCount search onSearchChange … />` — controlled, it never fetches. Server side: POST + `validator(list.querySchema)` → the usual permission gate → `runListQuery(listQueryBuilder(em, Entity, list), list.spec, data)` → DTO → `{ rows, rowCount }`; per-page scoping (ownership, grants) is a base condition on the qb BEFORE `runListQuery`. Row actions need page state, so they arrive through `rowContext={…}` (a list module must never import a server function that imports it back). Pickers NEVER reuse a paginated list function: add a `list<X>OptionsFn` (GET, full set). Rows that are not database-backed (agent-backed file browser) use the same declaration with `mode: 'client'` + `<ListTable>` (TanStack filters/sorts/paginates in the browser). Reference: `src/lists/servers.tsx` + `src/routes/admin/servers/index.tsx`.
- **Search params**: values are STRINGS in both directions (`src/lib/search-params.ts` wired into `createRouter`) — the router's own parser converts `?status=true` to a boolean and `?q=123` to a number, which breaks list filters. Query schemas coerce what they need (`z.coerce.number()` for paging); unrelated routes keep plain string params.
- **Server functions**: in `src/server/functions/` — THIN: `requireUser()` / `requirePanelPermission(...)` (auth, `src/server/session.ts`), `.validator()`, `.middleware([withOrmContext])`, then calls into a SERVICE (`src/server/*.ts`: servers, nodes, recipes, users…). Errors via `HttpError(status, message)`; the agent client is `src/server/agent/client.ts` (Bearer fetch, `AgentError`). Business logic NEVER lives in a handler — extract it to a service module (like custodia).
- **ORM access (RequestContext)**: EVERY server function that touches the DB uses `.middleware([withOrmContext])` (`src/server/middleware.ts`); non-function entry points (SFTP auth, better-auth hooks) wrap themselves in `runWithOrmContext` (`src/server/orm.ts`). Inside a context, use `orm.em` (`src/server/orm.ts` singleton) directly — MikroORM resolves the request-scoped fork (ONE identity map per request). NEVER `orm.em.fork()`, NEVER `initOrm()` inside handlers: outside a context the global EM throws (`allowGlobalContext: false`), a fork splits the identity map. Services take NO em parameter — they use `orm.em` like custodia (`getMembersByOrganizationId` style).
- **Settings**: Pelican-style EAV — one `setting` row per namespaced key (`app:name`, `mail:smtp:host`), defaults in code (`SETTING_DEFAULTS` in `~/lib/settings`); DB rows are overrides only. Precedence: env var (`MOJITO_*` mapping, e.g. `MOJITO_MAIL_SMTP_HOST`) > DB row > default — env-forced keys are locked in the admin UI, skipped on write and refused by the update fns. Secrets (`mail:smtp:password`) are encrypted at rest and never round-tripped to the client (only `hasPassword`). `app:registration_enabled` is enforced server-side by the better-auth `hooks.before` (sign-up endpoints only) and drives `/register` + the login link. Page: `/admin/settings` (cards in `components/settings/`, permission `panel.settings`).
- **Users / roles / permissions** (Pelican-style, better-auth access control): ALL statements live in `src/lib/permissions.ts` (`createAccessControl` from `better-auth/plugins/access` — pure TS, client+server). Roles: three BUILT-IN ones (admin = everything, moderator = read-only admin area, user = baseline — code-defined, not editable) plus CUSTOM roles in the `role` table, managed from `/admin/roles` with a permission matrix; `user.role` holds a built-in name or a custom role id, and `resolvePanelRole` (session.ts) resolves it (custom roles may only carry panel-level statements — never `server.*`, and only a subset of their creator's own permissions). Per-server permissions (`server.*` statements): owner/admin hold the full set, anyone else needs a `server_user` grant row (JSON statements, sanitized against the catalog). Checks: server-side `requirePanelPermission(request)` (panel, resolves DB roles) and `loadServerWithPermission(serverId, user, request)` (per server; destructive actions use `requireServerOwner`); client-side `hasPermissions(list, request)` / `hasAdminAreaAccess(permissions)` — the session DTO (`SessionUser.permissions`, computed in `getSession`) carries the effective flat list, the server pages use the per-server `viewer.permissions` from `getServerFn`. User management (list/create/role/ban/delete) is DIRECT MikroORM (`server/functions/users.ts` — NOT the better-auth endpoints, whose checks only know the static roles; passwords hashed with `hashPassword` from `better-auth/crypto`). The better-auth admin plugin (`better-auth/plugins/admin`, mounted in `auth.ts` with `ac` + `roles` + the plugin `schema` option for the snake_case mapping of `ban_*`/`impersonated_by`) provides the model columns and enforces bans at session creation; its tables are plain MikroORM entities + hand-written migrations — the better-auth CLI NEVER generates migrations. A sub-user can only grant a subset of their own permissions (`isSubset`); the console JWT carries only the granted agent permissions (`toConsolePermissions` → the agent gates every WS message on them).
- **Console**: xterm.js (`@xterm/xterm` + `@xterm/addon-fit` + `@xterm/addon-unicode11` — Unicode 11 width tables so emoji measure 2 cells), dynamic imports in useEffect (SSR-safe), incremental log polling from the agent (`after=N` cursor).
- **Backups**: Pelican parity, push-based — the `backup` row (panel DB) is the source of truth; `server/functions/backups.ts` creates the row, orders the agent, and the LIST query syncs pending/running/restoring rows by polling the agent (404 → failed, "no frozen history"). Per-server limit: `server.backup_limit` (0 = disabled). Download: short-lived `backup-download` JWT (`signBackupDownloadToken`) → the browser streams the archive directly from the agent. Page: `/servers/$serverId/backups` (status chips, create form, restore merge/truncate with the shared `ConfirmDialog`, delete, polling while active).
- **Schedules**: Pelican "Schedules" parity — cron-triggered task chains (power actions / console commands, delay between tasks 0-900 s). Split of ownership: the `schedule` table (panel DB) owns the WHEN (`next_run_at` computed and persisted at write/claim time by `nextCronRun` in `~/lib/cron` — croner, evaluated in the schedule's own timezone, never on the fly), the runner (`server/schedules.ts`, started from `src/server.ts`) scans due schedules every 30 s and claims a run atomically (`is_processing` flipped in one conditional `nativeUpdate` — a tick racing a "run now" sees zero affected rows). pg-boss owns the HOW: each task is a durable job on the `schedule-task` queue and each job queues the next with `startAfter` — a chain SURVIVES a panel restart. `onlyWhenOnline` skips (consumes) the occurrence when the agent reports the server down. Anti-stuck: a boot sweep releases the claims of a previous process, a 3 h sweeper releases dead chains (`retryLimit: 0`, `expireInSeconds: 120`). Pages: `/servers/$serverId/schedules` (list + create dialog) and `schedules/$scheduleId` (edit + run-now + delete) share the form component `components/schedule-form.tsx` (both run `scheduleEditFormSchema`; the create wire schema strips `isActive`). Activity events: `schedule:create/update/delete/run`. Permission: `server.schedules` (`runScheduleNowFn` gates on `update`).
- **Queue (pg-boss)**: the panel's durable job engine (`server/queue.ts`, singleton, started at boot after the MikroORM migrations). pg-boss manages its OWN `pgboss` schema with its own internal migrations — its tables are NEVER mapped as MikroORM entities and never touched by our migrations (the schema is invisible to the public-schema diff, which is exactly what keeps `migration:create` clean; internals also change shape between pg-boss majors). Scheduling via pg-boss's own cron (`schedule: false` — the schedule table owns the WHEN). Access the queue only through `getQueue()`/`startQueue()`, never a second instance.
- **UI feedback**: toasts via sonner (`toast.success`/`toast.error` from the `sonner` package), NO inline success messages. `<Toaster richColors closeButton />` is mounted in `__root.tsx`. Destructive confirmations: the shared `ConfirmDialog` (`components/confirm-dialog.tsx`, shadcn AlertDialog) — NEVER native `confirm()`/`alert()`/`prompt()`.
- **Selects**: ALWAYS the shadcn component (`components/ui/select.tsx`), NEVER a native `<select>`. Recipe variable field (boolean/options/text/number): shared component `components/variable-field.tsx`. base-ui only resolves an item's label once its popup has opened — a closed trigger with a value shows the raw id: give `<SelectValue>` a render prop that resolves the label from the options (`components/data-table/data-table-filters.tsx` `FilterControl` is the reference).
- **List page actions**: the action button of a list page (create/import) lives in the list card's `CardAction` (top of the card, next to the title — see `/admin/recipes`), NEVER as a separate form card below the table. A create form opens in a Dialog from that button (see `CreateUserDialog` in `/admin/users`); pickers over another list use the shared `DataPicker` instead.
- **Server variables**: the `/servers/$serverId/variables` page edits the recipe's variables with a dynamic Zod schema (`makeUpdateServerVariablesSchema` in `validators/server.ts`, reuses `validateVariableValue` from the contract). The panel DB is the source of truth; the `updateServerVariablesFn` server function only merges `userEditable` variables, then pushes the sync to the agent (`servers.json` cache).
- **Types**: inferred from entities via `InferEntity` in `db/types.ts` (`I` prefix: `IUser`, `ISession`). NO hand-duplicated types.
- **Entities**: all in `db/entities.ts` with `defineEntity` + `p`. snake_case DB columns via `.fieldName()`, camelCase in TS.
- **Session**: fetched in SSR in `beforeLoad` of `__root.tsx` via `queryClient.fetchQuery({ queryKey: ['auth'] })`. After login/register: `queryClient.invalidateQueries({ queryKey: ['auth'] })`. On signOut: `queryClient.clear()` (never invalidate-all — active queries would refetch as guest and 401; 4xx never retry, see the retry policy in `router.tsx`).
- **First-run setup**: while the `user` table is empty, `__root.tsx` redirects every page to `/setup` (queryKey `['setup']` → `getSetupStatusFn`); `createFirstAdminFn` (`server/functions/setup.ts`) creates the first account with the built-in `admin` role and refuses (403) once any account exists; `/setup` redirects to `/` afterwards.
- **Usernames**: every user has a unique `username` (stored lowercased, `[a-zA-Z0-9_-]{3,32}` — no dots) — asked at setup, register and admin user creation. SFTP login is `{username}.{serverId}` (see `lib/sftp.ts`); the panel password is reused for SFTP.
- **IDs**: panel-generated ids are `nanoid()` from `~/lib/nanoid` (default 21 chars) — NEVER `randomUUID`. The contract accepts nanoid or legacy UUID (`idSchema` in `src/contract/api.ts`); shard mirrors it with `contract.IsID`.
- **shadcn components**: `ref` as a prop (React 19), no `React.forwardRef`.
- **Routes**: as directories. One page = one directory with `index.tsx`. Grouping via pathless layouts (`_auth/`).
- **DB**: Postgres — MikroORM manages ALL tables (including better-auth). Migrations at boot via `src/server.ts` (`orm.migrator.up()`). NEVER `schema.update()` (MikroORM v7 drops unknown tables by default). The better-auth snake_case mapping is in `src/lib/auth.ts` (`user.fields` etc.).
- **better-auth**: `baseURL: process.env.BETTER_AUTH_URL` — NO custom `trustedOrigins`. The dev server port is fixed in `vite.config.ts` (`strictPort: true`).

## Contract conventions (src/contract)

- **Recipe format v4** — feature parity with Pelican eggs (PTDL_v2), but declarative and Windows-first (no Docker, no mandatory bash script).
- **Variables**: `env` UPPERCASE (`MINECRAFT_VERSION`) + `{{ENV_VAR}}` templating everywhere. Fields: `name`, `type` (string/number/boolean), `default_value`, `user_viewable`, `user_editable`, `sort`, `required`, `min`/`max`, `pattern` (regex validation, equivalent of Pelican's Laravel `rules`), `options`.
- **Reserved system variables** (provided by the agent, not declarable): `SERVER_UUID`, `SERVER_NAME`, `SERVER_MEMORY`, `SERVER_PORT`, `SERVER_IP`, `SERVER_INSTALL_DIR`, `RUNTIME_DIR` (runtime installs only).
- **Runner actions**: `download`, `extract`, `write`, `replace`, `configFile` (`properties`/`ini`/`yaml`/`json` parsers — equivalent of Pelican's `config.files`), `command`, `script` (open fallback: `powershell`/`cmd` shell only — no bash).
- **Exit codes**: a `command` action can declare `successCodes` (exit codes accepted as success, default `[0]`). E.g.: steamcmd exits with 7 after its self-update even though the job succeeded.
- **Live progress**: a `command` action can declare `tail` (`file`, optional regex `filter`, `intervalMs`) — the agent follows the file and streams new lines during execution. On Windows the agent renders steamcmd's bare-`\r` progress live from stdout; `tail` remains available for tools that only log their progress to a file.
- **start**: `command`, `stop` (command/signal + `timeoutMs` → kill), `ready` (`pattern` + `strip` — equivalent of Pelican's `config.startup`), `workingDirectory`.
- **Others**: `logs` (stdout/file mode + stripAnsi), `updateUrl`, `backup` (`include`: glob patterns of the archive contents — relative POSIX, no `..`/absolute/drive/negation, `validateBackupIncludePattern`; absent = whole install dir, `.bin/` always excluded).
- Templating resolution: system variables > server variables > recipe defaults > fixed env.
- Unknown variable in a template = install-time error (`findUnknownVariables`).
- Zod schemas for: panel ↔ agent API requests/responses, WS messages.
- `schemaVersion` mandatory in every recipe JSON (v4 only).

## Tests

- Vitest (`tests/` next to `src/`).
- After any change: `npm test` must pass.
- List contract: `tests/list-query.test.ts` (query schema + the SQL each declaration generates, via a metadata-only Postgres ORM with `connect: false`), `tests/search-params.test.ts` (URL round-trip) and `tests/list-query.postgres.test.ts` (the same spec executed against the dev database — it skips itself when none is reachable, so `npm test` stays green without the dev stack).
